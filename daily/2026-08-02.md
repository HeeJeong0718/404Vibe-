# 외부 API 장애가 전체 서비스 장애로 확산된 이유

## 핵심 원인
- 외부 API가 **오류를 반환하지 않고 연결만 유지**했다.
- **타임아웃이 없어** 요청이 무한정 대기했다.
- 대기 중인 요청이 **스레드, 커넥션, 메모리 등의 서버 자원**을 계속 점유했다.
- 추천 기능과 핵심 기능이 **같은 자원을 공유**하고 있어, 결국 핵심 기능까지 영향을 받았다.

---

# 왜 타임아웃 + 재시도만으로는 부족한가?

## 타임아웃
- 무한 대기를 막기 위해 **반드시 필요**하다.
- 하지만 장애가 계속되면 **모든 요청이 타임아웃 시간만큼 기다린다.**
- 요청이 많으면 짧은 타임아웃이어도 대기 요청이 계속 쌓인다.

## 재시도(Retry)
- 일시적인 네트워크 오류에는 효과적이다.
- 하지만 **외부 서비스 자체가 장애인 상황에서는 오히려 호출을 더 늘려 부하를 증가시킨다.**
- 따라서 **횟수 제한 + 백오프**가 필수이며, 단독 해결책은 아니다.

> **내가 놓친 부분**
>
> "대기를 끊는 것(Timeout)"까지만 생각했고,
> **"계속 호출 자체를 막는 것(Circuit Breaker)"**을 고려하지 못했다.

---

# 재발 방지를 위한 설계

## 1. Timeout
- 무한 대기 방지
- 적절한 시간 내 응답이 없으면 즉시 종료

## 2. Circuit Breaker
- 장애가 반복되면 **외부 API 호출 자체를 중단**
- 즉시 실패 처리하거나 대체 결과(Fallback) 반환
- 장애 전파 방지

## 3. Bulkhead
- 추천 기능과 핵심 기능의 자원을 분리
- 추천 API가 자원을 모두 사용해도 핵심 기능은 영향받지 않음

## 4. Fallback
- 추천 API 실패 시 추천 영역만 제외하고 페이지 제공
- 핵심 서비스는 계속 동작

---

# 캐시와 프론트 분리

### 캐시
- 기존 추천 데이터를 제공할 수 있음
- 하지만 캐시 만료(Cache Miss)까지 해결하지는 못함

### 프론트엔드 분리
- 추천 위젯을 별도 요청으로 불러오면 초기 화면 영향 감소
- 하지만 백엔드 보호(Timeout, Circuit Breaker, Bulkhead)는 여전히 필요

---

# 핵심 암기

> **Timeout → 기다림을 끊는다.**

> **Circuit Breaker → 호출 자체를 끊는다.**

> **Bulkhead → 자원을 분리한다.**

> **Fallback → 실패해도 핵심 기능은 제공한다.**

# Stateless(무상태) 정리

## 1. Stateless란?

**Stateless(무상태)** 는 서버가 클라이언트의 상태를 저장하지 않는 구조이다.

즉, 서버가 다음 정보를 직접 기억하지 않는다.

- 로그인 상태
- 이전 요청 정보
- 사용자 세션 정보

필요한 정보는 **요청 자체에 포함해서 전달**한다.

대표적인 예:
- JWT 인증 방식

---

# 2. Stateful(상태 유지) 방식

서버가 사용자의 상태를 저장하는 방식이다.

예:

```
사용자
  |
  ▼
서버 A

서버 A 메모리:
user123 = 로그인 상태
```

이후 요청이 다른 서버로 이동하면:

```
사용자
  |
  ▼
서버 B

서버 B:
"나는 user123의 로그인 정보를 모름"
```

문제가 발생한다.

따라서 Stateful 구조에서는:

- 같은 사용자의 요청은 항상 같은 서버로 보내야 한다.
- Sticky Session(Session Affinity)이 필요하다.
- 특정 서버에 의존하게 된다.

---

# 3. Stateless 방식

서버가 상태를 저장하지 않고,
클라이언트가 필요한 정보를 함께 보내는 방식이다.

예: JWT 인증

로그인:

```
사용자
  |
  ▼
서버 A

JWT 발급
```

이후 요청:

```
사용자
  |
  | Authorization: Bearer JWT
  |
  ▼
서버 B
```

서버 B는 이전 로그인 정보를 몰라도 JWT를 검증한다.

즉:

```
서버 A 기억 ❌
서버 B 기억 ❌

JWT 정보 확인 ✅
```

그래서 어떤 서버가 요청을 처리해도 정상 동작한다.

---

# 4. 서버가 바뀐다는 의미

서버가 바뀐다는 것은 **도메인이 변경된다는 의미가 아니다.**

사용자는 계속 같은 URL을 사용한다.

예:

```
https://example.com
```

하지만 내부적으로는 로드밸런서가 여러 서버 중 하나를 선택한다.

구조:

```
사용자
  |
  ▼
Load Balancer

 ├── 서버 A
 ├── 서버 B
 └── 서버 C
```

사용자는 모르지만 요청마다 다른 서버가 처리할 수 있다.

예:

```
요청 1 → 서버 A
요청 2 → 서버 B
요청 3 → 서버 C
```

---

# 5. Stateless가 필요한 이유

서버를 여러 대 운영할 때 확장성이 좋아진다.

예:

```
기존

서버 A
서버 B
서버 C


트래픽 증가

서버 D 추가
```

Stateless 구조에서는 새 서버를 추가해도 바로 요청 처리가 가능하다.

왜냐하면 특정 서버가 사용자의 상태를 가지고 있지 않기 때문이다.

---

# 6. MSA와 Stateless 관계

MSA에서는 서비스를 여러 개의 서버로 분리한다.

예:

```
사용자

   |
   ▼

API Gateway

   |
   ├── 상품 서비스 서버
   ├── 주문 서비스 서버
   └── 결제 서비스 서버
```

트래픽 증가 시 서버를 쉽게 추가하기 위해 Stateless 구조를 선호한다.

하지만 Stateless는 MSA만의 개념은 아니다.

일반적인 서버 여러 대 구성에서도 사용할 수 있다.

---

# Stateful vs Stateless 비교

| 구분 | Stateful | Stateless |
|---|---|---|
| 상태 저장 | 서버가 저장 | 저장하지 않음 |
| 요청 처리 | 같은 서버 필요 | 어떤 서버든 가능 |
| 인증 방식 | Session | JWT 등 |
| 확장성 | 낮음 | 높음 |
| 특징 | 서버가 기억 | 요청이 정보를 전달 |

---

# 핵심 암기

## Stateful

> 서버가 기억한다  
> → 같은 서버 필요

## Stateless

> 요청이 정보를 가지고 온다  
> → 어떤 서버든 처리 가능

---

# 한 줄 정리

Stateless는 사용자의 상태를 특정 서버에 저장하지 않고 JWT 같은 정보를 요청에 포함시켜 전달하기 때문에, 로드밸런서가 요청을 여러 서버로 분산해도 정상적으로 처리할 수 있는 구조이다.

---

# 한 줄 정리

외부 API 장애 시에는 **Timeout으로 무한 대기를 막고, Circuit Breaker로 반복 호출을 차단하며, Bulkhead로 자원을 격리하고, Fallback으로 핵심 서비스만이라도 제공한다.**
