# 1부. CORS — "왜 막혔는지"부터 보기

## 1-1. 상황

프론트엔드와 API 서버가 서로 다른 도메인에서 운영 중이었다.
프론트에서 API를 호출하자 콘솔에 오류가 발생했다.

```
Access to fetch at 'https://api.404vibe.com/problems'
from origin 'https://app.404vibe.com' has been blocked by CORS policy
```

담당자가 AI에게 "CORS 에러 없애줘"라고 요청하자 API 서버에 다음이 추가됐다.

```
Access-Control-Allow-Origin: *
```

에러는 사라졌지만, 코드 리뷰에서 동료가 말했다.

> "일단 왜 CORS가 막고 있었는지부터 확인해야 한다."

---

## 1-2. 첫 번째 의문 — 브라우저가 읽는 건데, 왜 설정을 API가 하지?

### 검사는 브라우저가, 허락은 서버가

CORS 규칙을 실행(enforce)하는 건 브라우저가 맞다.
하지만 브라우저가 판단할 근거인 **"이 오리진한테 내 데이터를 줘도 된다"는 허가는 리소스 주인인 API 서버만 발급할 수 있다.**

브라우저는 그 허가증을 확인하는 검문소일 뿐이다.

만약 프론트가 자기 코드에 "나 허락됐음"이라고 선언할 수 있다면 그건 보안이 아니다.
악성 사이트도 똑같이 선언하면 되니까. **도둑이 자기 출입증을 직접 발급하는 셈.**

### CORS가 원래 막으려던 것

CORS는 프론트 개발자를 괴롭히려고 있는 게 아니라 **사용자를 보호**하려고 있다.

```
1. 사용자가 bank.com에 로그인한 상태
2. 그 상태로 evil.com에 방문
3. evil.com의 JS가 bank.com/api/account 호출
4. 브라우저는 쿠키를 자동으로 실어 보냄
5. CORS가 없으면 → evil.com이 응답을 읽어간다
```

즉 CORS가 보호하는 대상은 **API 서버의 사용자**이지 프론트가 아니다.
그러니 설정 위치가 서버인 게 자연스럽다.

---

## 1-3. 두 번째 의문 — `*`가 왜 문제인가?

### 흔한 오해

> "`*`를 하면 모든 브라우저가 우리 API를 호출할 수 있게 된다"

**아니다.** CORS는 API에 대한 **접근 통제가 아니다.**

`*`가 없어도 지금 당장 누구나 curl이나 Postman으로 API를 때릴 수 있다.
서버 대 서버 호출에는 CORS가 **아예 적용되지 않는다.**
CORS는 오직 **브라우저 안에서 돌아가는 자바스크립트**에만 걸리는 규칙이다.

### `*`로 열었을 때 실제로 바뀌는 것

> 다른 웹사이트의 페이지가, **그 사이트를 방문한 사용자의 브라우저를 빌려서**, 우리 API 응답을 읽을 수 있게 된다.

"사용자의 브라우저를 빌린다"가 핵심이다.
그 요청은 **사용자의 IP, 사용자의 네트워크 위치**에서 나간다.

예를 들어 사내망에서만 접근 가능한 API라면,
직원이 악성 사이트 한 번 방문하는 것만으로 그 사이트가 사내 API를 읽어갈 수 있다.
쿠키는 `*`면 안 실리지만, **"네트워크 위치"라는 권한은 그대로 빌려준다.**

### `*`는 원래 원했던 것도 못 해준다

스펙상 `*`와 인증정보(쿠키, `Authorization` 헤더)는 **같이 못 쓴다.**

```js
fetch(url, { credentials: 'include' })  // ← 이 순간 * 는 거부됨
```

"에러가 사라졌다"는 건 지금은 인증 없는 요청만 하고 있다는 뜻이고,
**나중에 로그인을 붙이는 순간 다시 터진다.** 임시방편이다.

---

## 1-4. 세 번째 의문 — CORS는 AJAX에만 적용되나?

정확히는 **"자바스크립트가 응답을 읽으려는 요청"**이다.
`fetch`, `axios`, `XMLHttpRequest` — 실무에서 말하는 AJAX가 여기 해당한다.

### CORS가 안 걸리는 것들

```html
<img src="https://other.com/pic.png">      <!-- 그냥 뜸 -->
<script src="https://cdn.com/lib.js">      <!-- 그냥 실행됨 -->
<link href="https://cdn.com/style.css">    <!-- 그냥 적용됨 -->
<form action="https://other.com/submit">   <!-- 그냥 전송됨 -->
```

**자바스크립트가 내용을 읽을 수 없기 때문**이다.
이미지는 화면에 그려지기만 하고, 스크립트는 실행되기만 한다.
JS가 그 픽셀이나 소스코드를 읽어갈 방법이 없으니 정보 유출이 아니다.

> 다른 도메인 이미지를 canvas에 올려서 `getImageData()`로 픽셀을 읽으려 하면 그 순간 막힌다.
> **읽으려는 시도**가 생겼으니까.

### 한 줄 기준

> **"JS가 응답 내용에 손댈 수 있나?"** → 그렇다면 CORS 대상.

### 실무 함정

CORS는 **읽기 권한을 통제하는 규칙**이지, 요청을 보내는 걸 막는 규칙이 아니다.
사실 요청은 서버까지 이미 갔다 온 경우가 많다.
응답이 돌아온 다음에 브라우저가 "이건 너한테 안 줌" 하고 JS에게만 숨기는 것이다.

> 콘솔엔 CORS 에러가 떴는데, **서버 로그엔 요청이 정상 처리돼 있고 DB에도 데이터가 들어가 있는** 상황.
> POST의 경우 실제로 종종 겪게 된다.

---

## 1-5. 네 번째 의문 — 오리진을 우리 걸로 좁히면 안전한가?

방향은 맞지만 **범위가 생각보다 좁다.** 정확히는 이 한 가지 경로만 막힌다.

> 다른 오리진의 JS가 우리 API 응답을 읽어가는 것

### 막히지 않는 것들

**1) XSS는 전혀 못 막는다 (제일 중요)**

공격자가 우리 프론트에 스크립트를 심는 데 성공했다면,
그 스크립트는 **우리 오리진에서 실행된다.**
브라우저 입장에선 우리 코드와 구별이 안 되고, CORS는 당연히 통과시킨다.

> CORS를 아무리 좁혀도 XSS 앞에선 무의미하다.
> 순서가 반대다 — XSS를 막는 게 우선이고, CORS는 그 다음.

**2) 토큰이 털리면 의미 없다**

공격자가 액세스 토큰을 손에 넣었다면 그냥 자기 서버에서 curl로 호출한다.
브라우저를 안 쓰니 CORS가 개입할 자리가 없다.
`Origin` 헤더도 마음대로 위조할 수 있다 (브라우저만 이걸 못 바꾼다).

**3) 요청 자체는 막히지 않는다 (CSRF)**

악성 사이트가 `POST /api/transfer`를 날리면 응답은 못 읽지만 **송금은 이미 실행된다.**
데이터를 훔치는 게 목적이 아니라 뭔가를 실행시키는 게 목적이면 CORS는 무력하다.

### CORS의 정확한 위치

| 위협 | 막는 것 |
|---|---|
| 다른 사이트 JS가 응답 읽기 | **CORS** |
| 우리 사이트에 스크립트 주입 | XSS 방어 (입력 이스케이프, CSP) |
| 남의 자격증명으로 호출 | 인증/인가 |
| 의도치 않은 요청 실행 | SameSite 쿠키, CSRF 토큰 |

CORS는 이 표의 **한 줄일 뿐**이고, 나머지 세 줄은 각자 따로 챙겨야 한다.

---

## 1-6. 그래서 어떻게 설정하나

### 에러 메시지의 진짜 의미

`blocked by CORS policy`가 뜬 이유는 정확히 이것이다.

> 응답에 **이 오리진을 허용한다는 헤더가 없었다**

- 아예 설정이 없었거나
- 설정은 있는데 **다른 주소로** 되어 있었거나

어느 쪽이든 브라우저 입장에선 똑같이 "허가증 없음"이라 차단한다.
실무에선 로컬 개발 주소(`localhost:3000`)를 빼먹어서 나는 경우가 제일 흔하다.

### 올바른 응답 헤더

```
Access-Control-Allow-Origin: https://app.404vibe.com   ← 우리 프론트만
Access-Control-Allow-Credentials: true
Access-Control-Allow-Methods: GET, POST, PUT, DELETE
Access-Control-Allow-Headers: Content-Type, Authorization
```

### 챙길 것 3가지

**① 환경별 화이트리스트**

운영, 스테이징, 로컬 주소를 목록으로 관리하고,
요청의 `Origin`이 목록에 있으면 **그 값을 그대로** 돌려준다.

> 헤더 값에 여러 개를 콤마로 나열하는 건 스펙상 안 된다. 딱 하나거나 `*`거나.

**② 인증을 쓸 거면 오리진 명시는 필수**

`Access-Control-Allow-Credentials: true`는 `*`와 같이 못 쓴다.

**③ preflight (OPTIONS) 처리**

`Content-Type: application/json`이나 `Authorization` 헤더를 쓰는 순간
브라우저가 본 요청 전에 `OPTIONS`를 먼저 보낸다.
서버가 이걸 200으로 받아주고 허용 메서드/헤더를 응답해야 한다.

> 여기서 막히면 "요청은 갔는데 서버 로그엔 OPTIONS만 찍혀 있다"는 상황이 나온다.

---

## 1-7. 1부 결론

> **"에러를 없앤 것"과 "요청이 허용되어야 하는지 판단한 것"은 다르다.**
> `*`는 판단을 건너뛰고 에러만 지운 것이다.

동료가 "왜 막혔는지부터 확인하라"고 한 건 결국 이 질문이었다.

**이 API는 원래 누가 써도 되는 건가?**

| 답 | 조치 |
|---|---|
| 공개 데이터, 아무나 읽어도 됨 | `*` 써도 괜찮다 |
| 우리 프론트만 쓸 API | 우리 오리진만 명시 + **인증도 함께** |

두 번째 경우, CORS를 좁히는 것만으로는 부족하다.
CORS는 브라우저만 막으니 **진짜 보호는 인증/인가가 해야 한다.**
CORS 좁히기는 그 위에 얹는 방어층이지 자물쇠 자체가 아니다.

# 2부. DB 데드락 — 잠금 순서를 통일하기

## 2-1. 상황

사용자끼리 자신이 만든 문제의 **소유권을 서로 교환**하는 기능.
AI가 구현한 로직은 하나의 트랜잭션 안에서 두 문제의 소유자를 차례대로 변경하는 방식이었다.

한 명씩 테스트했을 땐 정상이었지만, A와 B가 거의 동시에 교환 요청을 보내자 간헐적으로 실패했다.

```
A의 요청: 문제 101 수정 → 문제 202 수정 시도
B의 요청: 문제 202 수정 → 문제 101 수정 시도
→ 둘 중 하나의 트랜잭션이 DB에 의해 롤백

Deadlock found when trying to get lock
```

---

## 2-2. 가장 쉬운 비유 — 볼펜과 지우개

책상에 볼펜 하나, 지우개 하나가 있고 두 사람이 숙제를 하려면 **둘 다** 필요하다.

- **민수**: 볼펜을 먼저 집는다 → 이제 지우개를 집으려 함
- **영희**: 지우개를 먼저 집는다 → 이제 볼펜을 집으려 함

민수는 영희가 지우개 놓기를 기다리고, 영희는 민수가 볼펜 놓기를 기다린다.
**둘 다 하나씩 쥔 채로 영원히 멈춘다.** 이게 데드락이다.

> 혼자 테스트할 땐 절대 안 난다. 둘이 **거의 동시에** 집어야만 생긴다.
> "한 명씩 테스트할 땐 정상"이었던 게 정확히 이것이다.

### 해결: 규칙을 하나 정한다

> **"누구든 볼펜을 먼저 집는다. 지우개는 그 다음."**

민수가 볼펜을 먼저 잡으면 영희는 볼펜 앞에서 그냥 기다린다.
**손에 아무것도 안 쥔 채로.**
민수가 끝내고 둘 다 내려놓으면 영희가 가져간다.
서로 붙잡고 버티는 상황 자체가 안 생긴다.

핵심은 "누가 먼저냐"가 아니라 **모두가 같은 순서를 쓴다**는 것.

---

## 2-3. 평소의 "동시성"과는 다른 건가?

**같은 계열이다.** 데드락은 동시성 문제의 **한 종류**다.
다른 메커니즘이 아니라, 같은 락인데 상황이 꼬인 경우다.

### 1단계 — 자원 1개, 두 명이 동시에 (보통 말하는 "동시성")

재고 차감, 좌석 예약, 좋아요 카운트. 둘 다 같은 행 하나를 건드린다.

```
A: 101번 행 잠금 → 수정 → 커밋 → 해제
B:              ↑ 여기서 대기 ..... → 이제 진행
```

B는 **기다리면 된다.** 조금 느려질 뿐 실패하지 않는다.

> 여기서의 진짜 위험은 락 자체가 아니라, 락을 안 걸었을 때 생기는 **lost update**다.
> (둘 다 재고 10을 읽고 각자 9로 써서 1개만 줄어드는 것)

### 2단계 — 자원 2개, 순서가 엇갈림 (데드락)

```
A: 101 잠금 성공 → 202 요청 → 대기
B: 202 잠금 성공 → 101 요청 → 대기
```

**기다려도 절대 안 풀린다.**
A가 놓으려면 202를 받아야 하고, 202를 놓으려면 B가 끝나야 하고,
B가 끝나려면 101을 받아야 한다. **원이 닫혀버렸다.**

그래서 DB가 개입한다.
"이대로 두면 영원히 안 끝나겠네" 하고 감지해서 **한쪽을 강제로 죽인다.**

### 비교

| | 1단계 (락 대기) | 2단계 (데드락) |
|---|---|---|
| 자원 개수 | 1개 | 2개 이상 |
| 결과 | 기다렸다 성공 | 한쪽 강제 롤백 |
| 증상 | 느려짐 | 에러 |

### 데드락이 생기는 조건 (둘 다 만족해야 함)

1. 두 요청이 **같은 자원들을 공유**하고
2. **접근 순서가 반대**일 때

> "동시에 눌렀다"만으론 부족하다.
> A의 버튼이 하우스 행만, B의 버튼이 플레이어 행만 수정한다면 **데드락은 안 난다.**
> 겹치는 자원이 없으니까.

## 2-4. 앱 예시 ① — 송금 앱

계좌 이체는 딱 두 행을 건드린다. 보내는 사람 차감, 받는 사람 증가.

```java
@Transactional
public void transfer(long fromId, long toId, int amount) {
    accountRepo.decrease(fromId, amount);   // 1) 내 계좌 잠금
    accountRepo.increase(toId, amount);     // 2) 상대 계좌 잠금
}
```

### 터지는 순간

민수(계좌 101)와 영희(계좌 202)가 밥값 정산하다가
서로 "내가 보낼게" 하면서 **거의 동시에 송금 버튼**을 누른다.

```
[민수 폰] 영희에게 10,000원  →  transfer(101, 202)
[영희 폰] 민수에게 5,000원   →  transfer(202, 101)
```

서버에서 벌어지는 일:

```
1ms  민수 요청: 101 잠금 ✅  (내 계좌에서 1만원 뺐다)
2ms  영희 요청: 202 잠금 ✅  (내 계좌에서 5천원 뺐다)
3ms  민수 요청: 202 잠금 요청 → ⏳ 영희가 쥐고 있음
4ms  영희 요청: 101 잠금 요청 → ⏳ 민수가 쥐고 있음
     ...
5ms  DB: "얘네 서로 기다리네" → 영희 트랜잭션 강제 롤백
```

영희 화면에만 **"송금에 실패했습니다"**가 뜬다.
QA가 혼자 테스트할 땐 100번 해도 안 나오는 버그다.

### 고치기 — 계좌번호 순서로 잠근다

```java
@Transactional
public void transfer(long fromId, long toId, int amount) {
    long first  = Math.min(fromId, toId);
    long second = Math.max(fromId, toId);

    // 잠그는 순서만 통일. 돈 계산은 원래 방향 그대로.
    Account a = accountRepo.findByIdForUpdate(first);   // SELECT ... FOR UPDATE
    Account b = accountRepo.findByIdForUpdate(second);

    accountRepo.decrease(fromId, amount);
    accountRepo.increase(toId, amount);
}
```

이제 민수 요청도 영희 요청도 **똑같이 101 → 202** 순으로 잠근다.

```
민수 요청: 101 잠금 ✅ → 202 잠금 ✅ → 커밋 → 전부 해제
영희 요청: 101 앞에서 대기 ⏳ .................. → 이제 진행 ✅
```

영희는 **아무것도 안 쥔 채로** 기다린다.
손에 쥔 게 없으니 민수를 막지 않는다. 몇 밀리초 늦게 처리되고 끝.

## 2-5. 앱 예시 ② — 친구 맺기

양방향 행을 만드는 구조라고 하자.

```java
@Transactional
public void addFriend(long me, long other) {
    friendRepo.insert(me, other);    // 1) 내 쪽 행
    friendRepo.insert(other, me);    // 2) 상대 쪽 행
}
```

A와 B가 동시에 서로에게 요청하면:

```
A의 요청: (1,2) 삽입 → (2,1) 삽입 시도
B의 요청: (2,1) 삽입 → (1,2) 삽입 시도    ← 순서 반대
```

유니크 인덱스에 락이 걸리면서 서로 물린다.

### 고치기

```java
@Transactional
public void addFriend(long me, long other) {
    long first  = Math.min(me, other);
    long second = Math.max(me, other);

    friendRepo.insert(first, second);
    friendRepo.insert(second, first);
}
```

### 친구 맺기의 추가 함정

데드락을 고쳐도 이 시나리오는 여전히 이상하다.
**둘 다 성공하면 친구 관계가 두 번 만들어진다.**
데드락은 사라졌지만 중복이 남는다.

그래서 유니크 제약을 걸고, 중복 삽입 예외가 나면
"이미 친구입니다"로 처리하거나 무시하는 게 보통이다.

```sql
UNIQUE KEY uk_friend (user_id, friend_id)
```

## 2-6. 404Vibe 소유권 교환에 적용

```java
@Transactional
public void swapOwnership(long idA, long idB) {
    long first  = Math.min(idA, idB);
    long second = Math.max(idA, idB);

    Problem p1 = problemRepo.findByIdForUpdate(first);
    Problem p2 = problemRepo.findByIdForUpdate(second);

    long ownerA = p1.getOwnerId();
    p1.setOwnerId(p2.getOwnerId());
    p2.setOwnerId(ownerA);
}
```

A가 보내든 B가 보내든 무조건 `101 → 202` 순서. **순서가 뒤집힐 일이 없다.**

### 대응 관계

| 송금 앱 | 친구 맺기 | 404Vibe |
|---|---|---|
| 두 계좌의 잔액 | 두 친구 관계 행 | 두 문제의 소유자 |
| 서로 동시에 송금 | 서로 동시에 친구 요청 | 서로 동시에 교환 요청 |
| 계좌번호 순 잠금 | 유저 ID 순 잠금 | 문제 ID 순 잠금 |

## 2-7. 재시도가 왜 필요한가

볼펜/지우개만 있으면 규칙 하나로 끝나지만,
실제 DB는 **우리가 모르는 것들도 같이 잠근다.**

- 인덱스
- 외래키가 걸린 부모 행
- 다른 기능이 건드리는 같은 테이블

즉 **책상 위에 우리가 못 보는 물건이 더 있는 셈**이다.
"우리 코드에서는 순서를 지켰으니 이제 100% 안전"이라고 말할 수 없다.
**확률을 크게 낮추는 것이지 0으로 만드는 게 아니다.**

### 데드락은 성격이 특이하다

보통의 에러는 다시 해도 또 실패하지만,
데드락은 **타이밍이 겹쳐서 난 것**이라 다시 하면 대개 성공한다.
상대는 이미 끝났을 테니까.

```java
@Retryable(retryFor = DeadlockLoserDataAccessException.class,
           maxAttempts = 3,
           backoff = @Backoff(delay = 50, multiplier = 2))
public void swapWithRetry(long idA, long idB) {
    swapOwnership(idA, idB);   // 트랜잭션은 이 안쪽
}
```

> ⚠️ **재시도는 트랜잭션 바깥에서** 걸어야 한다.
> 이미 롤백된 트랜잭션 안에서 다시 시도해봐야 소용없다. 처음부터 통째로 다시 시작해야 한다.

## 2-8. 우리 몫과 DB 몫

흔한 오해: "A 끝나면 자동으로 B가 실행되게 코드를 짠다"

**그건 우리가 안 짠다.** 우리가 하는 건 **순서를 통일하는 것 하나뿐.**

```java
// 우리가 쓰는 코드는 이게 전부
long first  = Math.min(userA, userB);
long second = Math.max(userA, userB);
lock(first);
lock(second);
```

"A 끝나면 B 실행해" 같은 코드는 어디에도 없다.
B의 요청은 `lock(first)`에서 그냥 멈춰 서 있다가,
A가 커밋하고 락을 놓는 순간 **저절로 깨어나서** 다음 줄로 간다.

> 원래도 DB는 알아서 줄을 세우고 있었다.
> 다만 순서가 엇갈려서 **줄이 원형이 돼버린 것**이고,
> 우리는 **줄을 한 줄로 펴준 것**뿐이다.

| 우리가 짜는 것 | DB가 해주는 것 |
|---|---|
| 항상 같은 순서로 잠그기 | 뒤에 온 요청 줄 세우기 |
| 데드락 예외 시 재시도 | 데드락 감지하고 한쪽 롤백 |

---

## 2-9. 2부 결론

| | 하는 일 |
|---|---|
| **순서 통일** | 데드락이 **생길 일을 줄인다** |
| **재시도** | 그래도 생긴 데드락을 **사용자에게 안 보이게 한다** |

둘은 대체재가 아니라 **짝**이다.

- 순서만 맞추면 → 남은 확률에 사용자가 그대로 노출된다
- 재시도만 넣으면 → 자주 부딪히면서 계속 재시도하느라 느려진다

### 기억할 체크리스트

평소 "동시에 같은 데이터를 건드리면?"을 생각했다면, 여기에 이걸 얹는다.

> **"한 트랜잭션이 여러 행을 잠그나?"**
> 그렇다면 → **"항상 같은 순서로 잠그나?"**

**이 모양이 보이면 데드락을 의심한다:**

> "한 요청이 두 개의 행을 바꾸는데, 그 두 개가 **요청자에 따라 순서가 뒤집힌다**"

해당하는 기능들:

- 계좌 이체
- 소유권 교환
- 친구 맺기
- 매칭 / 짝짓기
- 데이터 병합
- 자리 바꾸기

> 단일 행 수정만 하는 기능에서는 데드락이 잘 안 난다.
