# 선착순 신청 동시성 문제 — 트랜잭션만으로는 부족한 이유

## ACID 정의
- **원자성(Atomicity)**: 작업이 전부 실행되거나 혹은 아예 실행되지 않아야 한다.
- **일관성(Consistency)**: 트랜잭션이 수행된 후에 DB 값은 일관된 상태여야 한다.
- **고립성(Isolation)**: 각 트랜잭션은 다른 트랜잭션의 작업에 영향을 받지 않아야 한다.
- **지속성(Durability)**: 성공적으로 완료되면 그 결과는 영구적으로 반영되어야 한다.

## 문제 상황

김피엠은 바이브코딩으로 선착순 100명인 404Vibe 오프라인 밋업 신청 기능을 만들었다.

여러 명이 동시에 신청되는 것을 막고자, 신청 로직 전체를 단일 트랜잭션으로 묶어달라고 AI에게 요청했고, AI가 다음처럼 구현했다.

1. 트랜잭션 시작
2. 현재 신청자 수 조회
3. 신청자 수가 100명 미만이면 신청 데이터 INSERT
4. 트랜잭션 COMMIT

테스트 완료 후 오픈했는데, 실제 서비스에서 마지막 1자리가 남은 시점에 여러 사용자가 거의 동시에 신청했더니, 최종 신청자가 103명이 되어버렸다. 분명히 신청 로직 전체를 트랜잭션으로 감쌌는데, 왜 이런 일이 발생했을까?

## 왜 발생했는가

A가 count를 읽음 → 그 순간엔 진짜로 정확한 값(99)이었음. 근데 A가 그 값을 들고 판단 → INSERT하는 그 짧은 사이에, B도 A의 커밋을 기다리지 않고 자기 나름대로 count를 읽어버림 → B도 99를 봄.

즉 문제는 **"잘못된 값을 읽었다"**가 아니라, **"읽은 시점엔 맞는 값이었지만, 그 값을 근거로 행동하기 전에 다른 트랜잭션이 같은 값을 근거로 먼저 치고 들어올 수 있는 틈이 있었다"**는 것.

이걸 DB 이론에서는 **Lost Update(갱신 유실)** 현상 또는 **TOCTOU(Time-Of-Check to Time-Of-Use) 레이스 컨디션**이라고 부른다. "더러운(uncommitted) 값을 읽어서" 생긴 문제가 아니라, "정확한 값을 읽었지만 그 값의 유효기간이 지나기 전에 여러 트랜잭션이 동시에 그 값을 근거로 행동해서" 생긴 문제라는 게 핵심 뉘앙스다.

## 정리


# DB row 락 vs UPDATE 문

row 락과 UPDATE 문은 같은 게 아니라, **"UPDATE 문을 실행하면 그 부수효과로 DB가 자동으로 row 락을 건다"**는 관계다.

- **row 락**: DB 엔진이 내부적으로 관리하는 잠금 메커니즘 그 자체 (개념/기능)
- **UPDATE 문**: 그 잠금을 자동으로 트리거하는 SQL 명령어 중 하나 (수단)

## SQL 명령별 row 락 여부

| SQL 명령 | row 락을 거는가? |
|---|---|
| 일반 `SELECT` | 원칙적으로 안 걺 (읽기는 대부분 락 없이 처리, MVCC로 스냅샷만 봄) |
| `UPDATE` / `DELETE` | 자동으로 해당 row에 exclusive 락을 걺 (별도 선언 없어도 DB가 알아서) |
| `SELECT ... FOR UPDATE` | 원래 읽기 전용인 SELECT에 명시적으로 락을 걸도록 강제하는 문법 |
